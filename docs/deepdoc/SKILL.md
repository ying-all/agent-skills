# deepdoc

给一个主题名，产出一篇**能读进去**的长文文档，而不是速查表或资料堆。

## 什么时候用

- 用户说「给我写一篇 XX 的文档 / 方法论 / 知识页 / 讲透 XX」
- 期望结果是**有结构、有推理、能跟着做**的长文
- 输出要能直接放进 GitHub、当笔记、当教程

不适用：API 参考、纯索引、新闻摘要、README 级别的短说明。

## 输出契约

| 项 | 约定 |
|---|---|
| 格式 | 单文件 HTML，离线可用，无 CDN、无外部字体 |
| 位置 | 默认 `D:\个人\Desktop\`；文件名 `<主题>-<YYYY-MM-DD>.html` |
| 中间产物 | 同目录保留 `<主题>.md`，方便二次修改和重新构建 |
| 规模 | 12–20 章，1.2 万字以上；章节数按主题复杂度定，不硬凑 |

## 工作流

### 1. 定题（只问一次）

从一句话里提取：主题、读者水平、边界（要不要覆盖攻防两面）。
信息不够就**一次问清**，给默认值，不要边写边问。

### 2. 检索（深度全靠这一步）

- 至少 3 个权威来源：官方文档 > 规范 > 厂商手册 > 高质量博客
- **版本敏感的事实必须核**：函数是否移除、默认值、参数名、报错原文
- 查不到的写「待验证」，不要编；编一个细节会毁掉整篇的可信度
- 记下来源，写进对应段落（一句话即可，不必做参考文献页）

### 3. 提纲

按 `references/outline.md` 的骨架裁剪。每章先用一句话写出**这章要证明什么**，再展开。
提纲先给用户看一眼（一句话列表即可），确认后再写正文。

### 4. 分章写作

一次写 3–4 章，追加到 md，避免一次输出被截断。全部写完后通读一遍，删掉重复段落。

### 5. 构建 + 自检

```bash
python assets/build.py --input "<主题>.md" --output "<主题>-<日期>.html" \
  --title "<标题>" --subtitle "<一句话简介>" \
  --chips "N 章|方法论|速查卡" --intro intro.md
```

构建后按下面的清单自检，不通过不交付。

## 深度标准（唯一硬指标）

一篇合格的 deepdoc：

1. **每个重要结论都带「为什么」或「什么时候不成立」**
   只写"应该用参数化查询"是废话；写出"为什么标识符不能参数化"才是深度。
2. **至少 5 处「只有查过才知道」的细节**
   版本差异、默认值、报错原文、性能上限、协议怪癖。
3. **每章至少一个结构化元素**：表格 / 代码块 / 决策树 / 对比矩阵
4. **有反面**：错误做法、失败案例、常见误判
5. **有可执行部分**：SOP、命令、检查清单

禁止：正确的废话、无来源的数字、"众所周知"、把目录当内容。

## 写作要求

- 中文，第二人称，短句；一段不超过 4 行
- 术语首次出现给中英对照，例如「闭合（quote breaking）」
- 代码块标注语言；命令保证可复制即用
- 表格列数 ≤ 6，单元格不写长段落
- **不要自己写「目录」章节**，构建脚本会生成

## 自检清单

- [ ] 每个 h2 都出现在左侧导航里，锚点可跳转
- [ ] 每个代码块语言标注正确，复制按钮可用
- [ ] 表格在窄屏下可横向滚动，没有被截断
- [ ] 所有版本敏感的事实都核过，或标注「待验证」
- [ ] 断网打开无报错、无空白
- [ ] 全文没有「待补充」「TODO」
- [ ] 至少一处能让人"哦，原来如此"的洞察

## 文件结构

```
deepdoc/
├── SKILL.md              # 本文件
├── README.md             # 给使用者的说明（可直接放 GitHub）
├── assets/
│   ├── build.py          # md -> html
│   ├── doc.css           # 版式
│   ├── doc.js            # 目录高亮 / 搜索 / 复制 / 清单记忆
│   └── vendor/           # 内置 Python-Markdown，免安装
└── references/
    └── outline.md        # 方法论骨架
```
